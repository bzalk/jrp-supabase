# Multi-Instance Supabase

This repository now has provisioning scripts for repeatable self-hosted Supabase instances on the same VPS.

## Goal

Keep the current stack intact, then generate additional isolated stacks such as:

- `supabase-upwork.jamrockdev.com` + `studio-upwork.jamrockdev.com`
- `auth-upwork.jamrockdev.com`
- `supabase-client-a.jamrockdev.com` + `studio-client-a.jamrockdev.com`
- `supabase-demo.jamrockdev.com` + `studio-demo.jamrockdev.com`

Each generated instance gets:

- its own `.env`
- fresh auth/JWT/API secrets
- its own bind-mounted `volumes/`
- its own host ports
- its own compose project name
- helper scripts for `up`, `down`, and `config`
- a dedicated Authelia instance with its own admin user
- Traefik labels for API + Studio + Auth routing
- a Caddy proxy snippet for environments that use shared Caddy

## How It Works

Run the guided installer:

```bash
cd /root/supabase/docker
./utils/deploy-instance.sh
```

The script will:

- prompt for a Netlify API token the first time and store it locally in `docker/supabase-instance-install/netlify.env`
- ask for the base domain, such as `jamrockdev.com`
- ask for the instance suffix, such as `upwork`
- create the `A` records for API, Studio, and Auth in Netlify DNS
- wait until those hostnames resolve before continuing

You can still run the lower-level generator directly:

```bash
cd /root/supabase/docker
./utils/create-instance.sh upwork
```

That creates:

```text
docker/instances/supabase-upwork/
```

Inside that directory:

- `docker-compose.yml` is copied from the current base stack
- `docker-compose.instance.yml` overrides container names and enables a dedicated instance-local `authelia` service
- `docker-compose.instance.yml` also adds Traefik labels for the generated API, Studio, and Auth hostnames
- `.env` is copied and then rewritten with instance-specific URLs, ports, tenant ids, and fresh secrets
- `volumes/authelia/` is generated with a per-instance Authelia configuration and user database
- `volumes/db/data` and `volumes/storage` start empty, so the new instance is not sharing live data with the original stack

## Port Scheme

Ports are allocated automatically by scanning:

- the base stack `.env`
- existing generated instance `.env` files
- currently listening host ports

The next free ports are used for:

- Studio
- Kong HTTP
- Kong HTTPS
- Postgres
- Pooler
- Authelia loopback

## Reverse Proxy

Each generated instance adds Traefik labels directly to its `kong`, `studio`, and `authelia` containers, so the active edge proxy can discover the instance without a shared-port restart.

It also writes:

```text
proxy/supabase-<slug>.caddy
```

That file contains host-port reverse proxy rules for:

- `supabase-<slug>.<base-domain>` -> local Kong HTTP port
- `studio-<slug>.<base-domain>` -> local Studio port
- `auth-<slug>.<base-domain>` -> local Authelia port

If you are using the shared Caddy setup instead of Traefik, then:

```bash
./utils/sync-caddy-routes.sh
./utils/reload-caddy.sh
```

If you create with `--up`, the script now waits for local health checks and then verifies the HTTPS routes through the active edge proxy, including the per-instance auth host. On this host, that means Traefik and no extra proxy restart is needed.

The shared [Caddyfile](/root/supabase/docker/Caddyfile) keeps a managed section for generated instance routes.

## Lifecycle

Create only:

```bash
./utils/create-instance.sh upwork
```

Create, start, and wait for proxied HTTPS:

```bash
./utils/create-instance.sh upwork --up
```

Full deploy with interactive DNS automation:

```bash
./utils/deploy-instance.sh
```

Full deploy with explicit arguments:

```bash
./utils/deploy-instance.sh upwork
```

Inside the generated instance directory, the local lifecycle commands are still:

```bash
./config.sh
./up.sh
./down.sh
```

## Safety Notes

- The generator intentionally does not copy `volumes/db/data` or `volumes/storage` from the existing instance.
- Fresh keys are generated by reusing the existing `utils/generate-keys.sh` and `utils/add-new-auth-keys.sh` scripts.
- A fresh Authelia admin password is generated unless you pass `--admin-password`; the plaintext is written to `authelia-admin.generated.txt` inside the instance directory.
- `SITE_URL` is left unchanged unless you pass `--site-url`, because that value depends on the application using the instance, not just the Studio hostname.
- `deploy-instance.sh` stores the Netlify token in a local ignored file at `docker/supabase-instance-install/netlify.env`.
- `deploy-instance.sh` creates `A` records only and waits for DNS resolution before provisioning continues.
- `deploy-instance.sh` waits for both direct host-port health checks and proxied HTTPS checks through the active edge proxy.
